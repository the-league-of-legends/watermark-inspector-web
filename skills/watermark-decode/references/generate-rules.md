# 从项目编码实现生成规则

适用于用户指定工程并要求生成／恢复规则。Skill 负责阅读源码理解算法，随附命令负责确定性编译与核对；命令不是通用源码反编译器。

## 找到真实写入格式

1. 在用户指定的工程或当前 Git 工程内，先遵循仓库规则，检查现有 `watermark.schema.json`、`watermark.schemas/` 和生成的测试向量。仅搜索本工程与明确依赖，不扫描所有仓库。
2. 用 `rg` 定位实际水印编码入口、数据写入函数及其调用，跟踪字段来源、位顺序、位数、符号、范围、时间起点／步长和字符串格式。不要把函数参数顺序或变量名直接当成线上的位布局。规则生成产物可能过期，需对照当前编码调用和常量。
3. 如果编码产物包含 `sourceRule` 或 `canonical`，优先恢复原定义；否则依据实际源码构造候选 JSON。沿用编码方已有的稳定 `projectKey` 和版本，不按本地目录名发明它们。缺少项目标识／版本、枚举顺序、时间参数等关键事实时，指出缺少哪个事实及源码位置；不能用猜测补齐。
4. GHCV8 才使用项目规则指纹。GHCV6/7 没有这种指纹，继续用旧协议读取，不能生成一个 GHCV8 规则并声称适用于旧图。其他纹理／纠错／协议需要开发适配器，规则文件不能适配任意算法。手写源码不能仅靠改文件生成新协议。

## 编译、核对与输出

有包含原规则和指纹的测试向量时：

```sh
watermark-decode generate-rules --project /path/project \
  --source /path/project/generated/vectors.json \
  --verify-source /path/project/EncoderSchema.java \
  --output /path/project/watermark.schema.json
```

只有手写实现时：根据步骤2提取定义，先写到临时候选文件，再以 `--source /tmp/candidate.json` 传入；`--verify-source` 指向真实编码常量文件。Android `FINGERPRINT`、iOS `kWatermarkSchemaFingerprint`、JS `schemaFingerprint` 的显式16位十六进制赋值可直接核对。其他写法需阅读并解释，返回候选而非伪造一个受支持的常量文件让校验通过。

- `--source` 可接受规则 JSON、包含 `sourceRule` 的生成产物，或含规范化 `canonical` 的产物。`--source` 省略时仅读取指定／当前工程根目录的规则文件。`--verify-source` 可重复。
- 命令不执行项目源码。使用相同核心校验字段、119位容量及指纹；有来源向量时核对完整消息、BCH码字及可选纹理哈希。不截断，也不为匹配而修改／缩短字段。
- `status=rules_ready` 只表示与提供的编码指纹／产物一致。来源包含文件路径及 SHA-256；报告需区分“来源产物核对”“当前源码核对”“实际图片验证”。它不能单独证明已安装的包正在使用该格式。
- 无可核对的指纹时返回 `needs_source_verification`，附候选规则，但不写正式文件。继续检查实际写入实现及历史规则；不把刚计算出来的指纹复制回源码充当证据。
- 缺规则时返回 `needs_source_analysis`，由 Skill 继续源码分析，而不是直接停止。若最终不能确定，给出具体缺项及候选状态。
- `--output` 是显式输出路径；不传则只输出 JSON。已有不同内容的文件拒绝覆盖，应保留历史规则并另存。不自动改 `watermark.analysis.json`，业务日志字段映射不是编码规则。
- 若提供了真实截图，使用新规则独立解码验证，只有 `status=decoded` 才声称图片验证通过。没有截图就明确未测图片；不能把合成向量当作实际运行验收。
- 错误输出具体原因；在自动分析流程中记录提醒并继续旧有取证，不补猜账号。

最后说明来源文件、项目／规则版本、指纹、使用位数、生成位置、核对层级及缺项。修改了格式或客户端实现时按工程要求检查其他编码器、Web、Python和自动分析工具联动；仅恢复同一规则不需要改协议。
